Point-in-time checks for ML pipelines

Coding agents write whole ML pipelines over relational data. The code runs, the tests pass, the score looks good. A model built to predict what happens after a date t can still use facts that appeared after t. STRATA runs each layer of the pipeline on the data as it is and on the data as it was at t. A difference in the output is a leak, and STRATA names the time, the entity, the column and the table it came from.

1Five layers, one rule

taskwho is in the prediction table at t, and whether labels are complete when they are used
featuresrows created after t, dates filled in later, values overwritten at the end of the data
modeltraining rows whose outcome was not known yet at t
in-contextfew-shot examples for an LLM taken from after t
agenta model that already knows the entity from outside the data

A check of one layer passes a pipeline that leaks in another. Agent-written training scripts often cut their features correctly and still train on outcomes from the future. STRATA checks all five layers with one rule and never reads the code:

output on D = output on D as of t

D as of t is the database at that moment: rows that did not exist yet are removed, and values that were filled in later are empty.

3The availability schema

STRATA does not know your database in advance. It needs a short schema that says, for every table, which column gives the time a row appears and which values arrive later. strata init drafts this schema from the raw files.

Rules based on column names and dates find most of it. They miss columns that are overwritten with the latest value, like an order status that always shows the final state. An optional LLM agent reads a profile of the data and proposes each decision with a reason. STRATA tests every decision against the data and a person confirms the result.

4.3Can the task table itself leak?

Yes. Before any feature is computed, the task table decides which customers are predicted at which date. A row for a customer who signs up later tells the model that this customer will exist, and that is a fact from the future. STRATA compares every task row with the customer's creation date from the schema. It also checks that labels use only events up to the end of their prediction window.

6The identity check

A pretrained model inside the pipeline, or an LLM that writes the predictions, may already know real drivers or users from public data, including what happened to them after t. STRATA replaces every ID with a made-up one and runs the script again. Nothing else changes: the rows, their order and which rows belong to one entity stay as they were. A script that learns only from the data gives the same predictions with real and with made-up IDs. A script whose predictions change took something from the real IDs.

STRATA uses two different renamings. If the predictions differ between the two renamings themselves, the script depends on how IDs are spelled, and recall of real entities cannot be separated from that. The verdict is then UNCHECKABLE.

7Results on eight databases

PITBench gives eight databases with hand-made answers. For each database it has control programs whose verdict is known, and a correct reference pipeline. We changed one time comparison in that pipeline at a time, for example <= into < or a removed date filter. Each changed version was labelled by hand as a leak or as harmless. A good checker flags the leaks and leaves the harmless changes alone. Pick a simpler checker to see where it fails.

7.3Kinds of change

drop_cutoffremoves a date filter, so later rows come in
future_offsetmoves a window past t
extend_horizonmakes the label window longer than the task allows
boundary_shiftturns < into <= or back
drop_lower_boundremoves the start of a window, which only adds older rows

The same kind of change can be a leak in one place and harmless in another. A window moved past t is harmless if another filter still cuts at t. So the label comes from a person and the verdict from running the code.
