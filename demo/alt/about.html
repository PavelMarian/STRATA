STRATA finds where an ML pipeline reads the future.

A checker for pipelines over time-stamped relational data, made for code that coding agents write. It runs your code on the data as it is and as it was at prediction time, and tells you where the two disagree.

What is a point-in-time leak?

You build a model to predict what happens to a customer, a product or a driver after a date t. Every number the model sees for that prediction must have been known at t. A review written a week later, a delivery date filled in after the fact, an order status overwritten at the end of the data, a training row whose outcome came after t: each of these makes the offline score look better than the model will ever be in production.

Why is this a problem now?

Coding agents write whole pipelines over relational databases, often ones nobody has annotated. The code runs, the tests pass and the metric is high. In our corpus, every one of 27 agent-written training scripts on RelBench learns from rows after the prediction time, and a metric gain would not have shown it: the AUC rose in only 17 of them.

What does STRATA do about it?

It never reads the code. For each layer of the pipeline it runs the code twice, on the full database and on the database as it was at t, and compares the outputs.

output on D  =  output on D as of t

A difference is a LEAK with a witness: the time, the entity, the column and the channel that carried the future. No difference at the tested times is CLEAN. If the output depends on a column whose availability nobody knows, the answer is UNCHECKABLE, never a false pass.

What does it need from me?

One short file per database, the availability schema: for each table, when a row appears and which values arrive later. strata init drafts it from the raw CSV or Parquet files; with --llm an LLM agent proposes each decision with a reason, STRATA checks every decision against the data, and the open questions go to the person who knows the data. You review the draft once.

pip install -e .
strata init --data path/to/csvs --out schema.json
strata check features --schema schema.json --program feats.py:get_features --entity product

How does a coding agent use it?

Exit codes 0, 1, 2, 3 for CLEAN, LEAK, UNCHECKABLE, ERROR and a JSON report make every check a gate. The agent loads SKILL.md, which says which check to call for which layer, how to read a witness, that only a rerun may declare a leak fixed, and that CLEAN is not a proof. Code under test runs in a child process with a timeout, a memory limit and no API keys in the environment.

What came before?

PITFALL studied point-in-time leakage in generated feature code on one database with a handwritten oracle. PITBench brought eight databases to one contract: an availability map, control programs with known verdicts and a reference pipeline each. STRATA is the checker that works on any of them, and on a database it has never seen, from a schema alone.
