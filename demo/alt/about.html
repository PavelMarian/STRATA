Your ML pipeline may be peeking at the future. STRATA shows you where.

A checker for pipelines over time-stamped relational data, made for code that coding agents write. It runs your code on the data as it is and on the data as it was at prediction time, and tells you where the two disagree.

What is a point-in-time leak?

You build a model to predict what happens to a customer, a product or a driver after a date t. Every number the model sees for that prediction must have been known at t. A review written a week later, a delivery date filled in after the fact, an order status overwritten at the end of the data, a training row whose outcome came after t: each of these inflates the offline score, and the model will never reach that score in production.

Why coding agents make it worse

An agent writes the whole pipeline, often over a database nobody has annotated. The code runs, the tests pass and the metric is high. The leak can sit in any of five places, and a check of one place passes a pipeline that leaks in another. In our corpus, agent-written scripts that cut their features correctly still trained on outcomes from the future.

One rule for all five

output on D  =  output on D as of t

STRATA never reads the code. For each layer it runs the code twice, on the full database and on the database as it was at t: rows that did not exist yet are removed, values filled in later are blanked. Then it compares the outputs.

A difference is a LEAK with a witness: the time, the entity, the column and the channel that carried the future. No difference at the tested times is CLEAN, and the verdict is scoped to those times. If the output depends on a column whose availability nobody knows, the verdict is UNCHECKABLE.

What it needs from you

One short file per database, the availability schema: for each table, when a row appears and which values arrive later. strata init drafts it from the raw CSV or Parquet files. With --llm, an LLM agent proposes each decision with a reason, STRATA checks every decision against the data, and the open questions go to the person who knows the data. You review the draft once.

pip install -e .
strata init --data path/to/csvs --out schema.json
strata check features --schema schema.json --program feats.py:get_features --entity product

How a coding agent uses it

Exit codes 0, 1, 2, 3 for CLEAN, LEAK, UNCHECKABLE, ERROR and a JSON report make every check a gate. The agent loads SKILL.md, which says which check to call for which layer, how to read a witness, and that only a rerun may declare a leak fixed. Code under test runs in a child process with a timeout, a memory limit and no API keys in the environment.

Does it work?

STRATA was tested on eight relational databases with known answers (PITBench), on feature programs written by code models, and on training scripts written by a coding agent.

What was testedWhat STRATA found
Eight databases, 98 hand-labelled changes to a reference pipelineall 43 leaking changes caught, none of the 55 harmless ones flagged
The usual shortcut: cut the rows at tfinds fewer than half of the leaking programs, since it cannot see a value filled in later or a status overwritten at the end of the data
Olist, 134 feature programs written by code models16 leaks that a hand-written checker for Olist had passed, all through delivery dates filled in after t
RelBench, 27 training scripts written by a coding agentall 27 learn from rows after t, and in 10 of them the metric did not even rise

Names and dates in the raw files are enough to draft row times and late-filled dates. Columns overwritten at the end of the data need the LLM agent: the rules alone found 5 of 50 of them, the agent found all 50.

What came before

PITFALL studied point-in-time leakage in generated feature code on one database with a handwritten oracle. PITBench brought eight databases to one contract: an availability map, control programs with known verdicts and a reference pipeline each. STRATA is the checker that works on all of them, and on a database it has never seen, from a schema alone.
